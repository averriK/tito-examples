RETRIEVE FORMAT RULES — FORMAT-ONLY CLEANUP FROM RAW TEXT

Purpose
- Define what is allowed and forbidden when converting raw PDF/DOCX text into
  clean Markdown for the knowledge base, without changing the meaning of the
  content.
- These rules apply to the `retrieve` workflow only. They are stricter than
  session/compile formatting rules: no summarization, no conceptual rewriting.

Scope
- Inputs: linearized raw text extracted from a single document (written by the
  deterministic extraction step: external helper + CLI).
- Outputs: cleaned Markdown chunks and the final assembled retrieve Markdown
  output declared by the retrieve manifest (`outputs.primary`).
- Evidence/source of truth: the raw extracted text itself plus an optional
  References/Bibliography section at the end.

Core invariant (format-only contract)
- Apart from removing obvious PDF artifacts (headers/footers/page numbers) and
  fixing extraction glitches, the cleaned Markdown MUST preserve:
  - The same sentences and arguments as the raw text.
  - The same logical order of sentences and paragraphs.
  - The same set of concepts and claims (no additions, no deletions).
- You MUST NOT summarize, condense, or rewrite arguments. This workflow is a
  format conversion only.

Allowed transformations (per chunk)
- Whitespace and line breaks
  - Normalize spaces and blank lines.
  - Merge hard-wrapped lines into full sentences/paragraphs where that is
    clearly an artifact of extraction.
  - Ensure paragraphs are separated by blank lines in Markdown.
- Page artifacts
  - Remove repeated page headers and footers.
  - Remove standalone page numbers that clearly serve only as pagination.
- Headings
  - When a line is clearly a section title (standalone, surrounded by blank
    lines, or obviously formatted as a heading in the raw text), you MAY
    convert it to a Markdown heading (`#`, `##`, `###`) that matches its
    apparent level.
  - You MUST NOT invent new section titles that are not clearly present in the
    raw text.
  - You MUST NOT restructure the heading hierarchy beyond making explicit what
    is already there.
- Lists
  - When the raw text clearly contains bullet or numbered lists, you MAY
    normalize them to Markdown lists (`-`, `*`, `1.` etc.).
  - Do not merge multiple logically distinct list items into one, or split a
    single item into many.
- Tables and code blocks
  - Preserve tables and preformatted blocks where they are clearly indicated in
    the raw text.
  - If the retrieve manifest reports `helper.tables.detected_count = 0`, treat
    the deterministic helper as authoritative that no canonical tables were
    detected:
    - Do NOT convert linearized or tabular-looking text into Markdown tables in
      the cleaned body.
    - Keep such material as plain text, list-like lines, or short paragraphs
      unless the raw text already contains an explicit Markdown table.
  - Treat any code block as **opaque**:
    - Do NOT normalize whitespace, hyphenation, citations, or punctuation inside preformatted/code regions.
    - Do NOT insert audit footnotes or citation markers inside code blocks.
  - Otherwise, you MAY convert obvious tabular text to simple Markdown tables,
    but only when the structure is unambiguous.
- Math (allowed exception to "no rewriting")
  - Normalize clearly mathematical expressions to LaTeX syntax (`$...$`,
    `$$...$$`) in line with project-wide math rules (see `rules/format.session.md`
    and `rules/format.compile.md`).
  - This normalization is explicitly allowed even though it changes characters
    and symbols, provided that:
    - All numeric values, variables, and relationships remain identical to the
      raw text.
    - You do **not** invent new equations or alter the structure of existing
      formulas.
    - Ambiguous plain-text fragments that might be math but are not clearly
      equations should be left unchanged.

Forbidden transformations
- Conceptual changes
  - Do NOT drop sentences that contain substantive information, even if they
    seem redundant, unless they are clearly pure artifacts (e.g., a sentence
    consisting only of a page number).
  - Do NOT merge distinct concepts into a single sentence or paragraph.
  - Do NOT rephrase content into a different “voice” or style beyond minimal
    repairs for extraction glitches.
- Structural changes
  - Do NOT reorder paragraphs or mix content from distant parts of the document
    into a single block.
  - Do NOT invent new subsections, headings, or structure that is not present
    in the raw text.
- Summarization and gap-filling
  - Do NOT summarize or condense sections.
  - Do NOT add new explanations, examples, or background.
  - Do NOT fill gaps or "clarify" ambiguous passages by adding new material;
    ambiguity must remain visible.

Language and style
- Use neutral, technical Markdown without marketing or promotional language.
- You MAY fix obvious typos introduced by extraction (split words, broken
  hyphenation), but you MUST NOT rewrite entire sentences for style.
- Preserve the original language (English/Spanish/etc.) of the document; do
  not translate.

Interaction with citations and bibliography
- Inline citation formatting and BibLaTeX generation are governed primarily by
  `rules/citations.retrieve.md` and `rules/biblatex.md`.
- These format rules only allow you to:
  - Insert or adjust citation markers where they clearly correspond to
    existing references.
  - Normalize citation brackets/parentheses as needed for Markdown and
    `[@Key]` syntax.
- You MUST NOT invent new cited works; every citation must come from the
  document's own reference list.

Filesystem constraints
- Do NOT read orchestration logs (`agent.out`, `RUN_METADATA.txt`, etc.) as
  sources of text for retrieve.
- Work only on the prepared KB mirror and files under `SESSION_DIR` as
  provided by the CLI.

CITATION RULES — RETRIEVE (FROM REFERENCES TO [@Key])

Goal
- Define how the `retrieve` workflow detects, normalizes, and represents
  citations when converting a single PDF/DOCX into Markdown plus a
  `biblatex.bib` database.
- Unlike compile workflows, retrieve usually starts from plain-text references
  (e.g. a `References`/`Bibliography` section) rather than token citations.

Scope
- Inputs:
  - Linearized raw text extracted from the source document (single-document
    retrieve; produced by the deterministic extraction step: external helper + CLI).
  - A References/Bibliography section near the end of that text.
- Outputs:
  - A Markdown document that uses only `[@Key]` citations in the body.
  - A `biblatex.bib` file with one entry per `@Key`.

Step 1 — Build reference table from tail
- Inspect only the tail region of the extracted raw text file (e.g., last
  500–1000 lines) to locate the start of the
  `References`/`Bibliography` section.
- For each reference entry in that section:
  - Parse authors, year, title, venue/journal/booktitle, and identifiers
    (DOI, URL, arXiv ID) where present.
  - Assign a stable citekey `@Key` using the global rules:
    - Pattern: `^[A-Za-z][A-Za-z0-9]{2,64}$`.
    - Prefer `AuthorYear` format (e.g., `Kramer2015`).
    - For collisions, append `a`, `b`, `c` (e.g., `Kramer2015a`).
  - Store a mapping from reference identity to `@Key` and full metadata.

Step 2 — Detect in-text citations
- When cleaning each chunk of the main body (not the references section):
  - Identify common citation patterns such as:
    - `(Author, Year)` or `(Author et al., Year)`.
    - `Author (Year)` style.
    - Numeric references like `[1]`, `[2,3]` when they clearly match entries in
      the reference list.
  - For each detected citation:
    - Locate the corresponding reference entry in the table built in Step 1.
    - If a unique match is found, replace the original citation token with the
      appropriate `[@Key]`.
    - If multiple references could match, or no match is clear, leave the
      citation text as-is and explain ambiguity only if necessary; do NOT
      invent a new key.

Step 3 — Representation rules
- In the final Markdown document produced by retrieve:
  - All machine-structured citations MUST use `[@Key]` syntax.
  - It is acceptable to retain human-readable citation text (e.g.,
    `Author (Year)`) when it is part of the prose, **in addition to** `[@Key]`,
    but the key must still appear so that BibLaTeX can be generated.
- Place `[@Key]` immediately after the sentence or clause it supports.
- Multiple keys are allowed when several works support the same statement,
  e.g. `... [@Kramer2015][@WellsCoppersmith1994]`.
- Never place `[@Key]` citations inside Markdown code blocks (fenced or indented), and do not attempt to normalize citation-like text inside code blocks.

Step 4 — BibLaTeX integration
- For every distinct `@Key` used in the body:
  - Create exactly one BibLaTeX entry in `biblatex.bib`.
  - Populate fields: `author`, `title`, `year`, `journal`/`booktitle`/
    `publisher`, `volume`, `number`, `pages`, `doi`, `url`, `eprint` as
    applicable.
  - Choose an appropriate entry type (`@article`, `@inproceedings`, `@book`,
    `@online`, `@misc`, etc.).
- Follow `rules/biblatex.md` for citekey and entry structure details.

Forbidden behavior
- Do NOT invent `@Key` entries for works that are not clearly present in the
  reference list or body.
- Do NOT convert arbitrary URLs in the body into citations unless they clearly
  correspond to a reference entry.
- Do NOT leave token-style citations (`[KB:/WEB:/DOI:/ARXIV:/ZOTERO:]`) in the
  final Markdown; if such tokens appear (e.g. from upstream tools), they must
  either be converted to `[@Key]` or left as plain text when mapping is not
  possible.

Output requirements
- The final retrieve `.md` document MUST:
  - Use only `[@Key]` markers for machine-readable citations.
  - Contain no unconverted token citations.
- The associated `biblatex.bib` MUST:
  - Contain exactly one entry per distinct key used in the body.
  - Be sufficient for downstream compile or LaTeX processing without manual
    patching.

BIBLATEX RULES — Minimal contract (MCP optional)

Goal
- Produce: (1) a compiled document that uses [@Key] citations, and (2) a BibLaTeX database file biblatex.bib with full entries for every cited key.

Citekeys
- Valid pattern: ^[A-Za-z][A-Za-z0-9]{2,64}$ (letters and digits only; start with a letter; unique per document).
- Key format by number of authors:
  - 1 author: AuthorYear (e.g., Kramer2015)
  - 2 authors: Author1Author2Year (e.g., WellsCoppersmith1994, AtkinsonBoore2006)
  - 3+ authors: FirstAuthorEtAlYear (e.g., BooreEtAl2014, AbrahamsonEtAl2016)
  - Organization/committee: OrganizationYear (e.g., SSHAC1997, ANCOLD2019)
- For collisions (same key pattern), append a, b, c: Boore2014a, Boore2014b.
- Use only the surname portion of each author name (no initials, no given names).
- This convention is mandatory for cross-session consistency: multiple sessions processing the same paper must produce the same citekey.

Metadata and entries
- For each token [KB:/DOC:/WEB:/DOI:/ARXIV:], construct a complete BibLaTeX entry with author(s), title, year, and venue/journal/booktitle/publisher as applicable.
- Put identifiers into fields (doi, url, eprint); never in the citekey. Fields may include punctuation; citekeys must not.
- Choose an appropriate entry type (@article, @inproceedings, @book, @online, @misc) based on the metadata.

Sources of truth
- Use your knowledge acquired during generation/compilation **only to complete or correct metadata (author, title, year, venue, identifiers) for works that are already identified from upstream citation tokens or existing [@Key] references.**
- If available, you MAY non-interactively call an MCP or local tool (e.g., RefChecker, Crossref, arXiv, OpenAlex) to verify/enrich metadata for those existing works. Do not prompt the user. Proceed even if external tools are unavailable.
- Do NOT introduce any new `[@Key]` citations or BibLaTeX entries for works that are not referenced by at least one `[KB:/DOC:/WEB:/DOI:/ARXIV:]` token or existing `[@Key]` in the input.

Deduplication
- If multiple tokens refer to the same work, use a single citekey and a single entry.
- Before creating ANY new citekey, search the existing biblatex.bib for the same work (match by DOI, title, or author+year). If found, reuse the exact existing key — do not invent a variant.
- If biblatex.bib already contains entries from prior slots or sessions, inherit those keys for the same works. Never generate a second key for a work that already has one.

Output
- Replace all inline token citations with [@Key] in the compiled document.
- When extracting citations/keys, ignore citation-like patterns that appear inside Markdown code blocks (fenced or indented).
- Create a file biblatex.bib containing exactly one entry per used key.
